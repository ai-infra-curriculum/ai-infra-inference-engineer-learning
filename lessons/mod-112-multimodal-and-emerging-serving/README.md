# Module 112 — Multimodal, Diffusion, and Emerging-Workload Serving

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 14

Modules 102–111 built the serving stack for the *text-completion* workload: the engine, the scheduler, the KV cache, the quantized weights, the multi-model surface, the distributed topology, the speculative decoder, the autoscaler, the observability stack, and the API front door. That workload is the majority of inference traffic in 2026, but it is not the whole of it. The product organisation already ships features that do not fit a pure text-completion mould — a chat that accepts screenshots, a design tool that calls a diffusion model, a voice interface that streams audio both ways, a reasoning model that thinks for forty seconds before answering, an agent that invokes tools in a loop for several minutes, a mobile app that keeps the model on-device so it works offline. Each of those is a serving shape in its own right, with its own batching rules, its own cache discipline, its own SLO vocabulary, and its own cost model.

This module is the inference engineer's compare-point for those shapes. It is explicitly *breadth before depth*: enough of each sub-shape that you can stand up a serving endpoint, reason about trade-offs, and decide which specialist peer to consult for depth. It is not a replacement for the specialist tracks on vision, speech, or on-device machine learning — it is the *serving-engineer's view* of those shapes, framed in the same scheduler / cache / SLO / cost vocabulary the rest of this curriculum uses.

By the end of it you can:

- **Deploy a vision-language model (VLM) serving endpoint** — image preprocessing on the ingress (decode, normalise, resize), the visual-token KV cache with per-image prefix hit semantics, the per-image token budget that caps a single request's visual-token spend, and the batching strategy across requests with variable image counts (0, 1, 3, 12) that keeps the batcher stable.
- **Deploy a diffusion serving endpoint** — image, video, and 3D diffusion; step-count control (the dominant latency knob); scheduler choice (DDIM vs. DPM-Solver vs. Euler vs. LCM / consistency-model distillation) as a latency / quality trade-off; denoising-batch patterns that amortise the UNet / DiT forward pass across concurrent prompts; VAE encode / decode as a separate cost axis.
- **Deploy streaming speech serving** — ASR (automatic speech recognition, Whisper-class) with streaming decode and partial-hypothesis emission; TTS (text-to-speech) with streamed audio response; audio chunking and endpoint detection; barge-in semantics (the user starts talking mid-TTS and the server must cancel the in-flight TTS and promote the ASR path).
- **Deploy reasoning-model serving** — long-think traces that may run for tens of seconds and emit tens of thousands of hidden tokens before the visible answer; the thinking-budget cap (`max_completion_tokens` / `reasoning_effort` / per-provider equivalents); interruptible decoding so an operator can stop a stuck long-think; the structured reasoning-vs-answer channel split that keeps the client's streaming UI sane.
- **Deploy agentic workloads at the serving edge** — long-running inference sessions (several minutes of model-driven tool-calls); the tool-call-heavy traffic shape (many short completions with high tool-response round-trip time rather than one long completion); the latency-bursty vs. token-bursty mix and what it does to batcher tuning; the per-session state and tool-timeout policy the ingress must enforce.
- **Make a server-side-vs-edge decision at build time** — a compare-point on the dominant edge / on-device runtimes (llama.cpp, Apple MLX, MLC-LLM, PyTorch ExecuTorch); the axes that drive the build-time decision (privacy, offline, cost per user, model-footprint, device-fragmentation, update cadence); the one-page RFC that lets a product manager and a mobile engineering lead sign off.

> **Prerequisites:** [Module 102](../mod-102-inference-engine-internals/README.md) (the engine lifecycle this module extends to new modalities), [Module 103](../mod-103-request-scheduling-and-batching/README.md) (continuous batching — the mechanism each sub-shape stresses differently), [Module 104](../mod-104-kv-cache-management/README.md) (visual-token cache is a prefix-cache specialisation; reasoning-trace cache is a KV-reuse specialisation), [Module 106](../mod-106-multi-model-and-adapter-serving/README.md) (multiple model classes on the same platform — a diffusion UNet and an LLM live on different replicas), [Module 110](../mod-110-observability-slo-and-cost/README.md) (TTFT / TPOT for text does not translate verbatim to diffusion steps or audio chunks; this module renames the axes), [Module 111](../mod-111-inference-api-and-protocols/README.md) (the API surface this module extends with multimodal content parts, audio endpoints, reasoning channels, and MCP tool shapes).

## The core framing

Multimodal and emerging serving is not "text serving plus pictures." Four asymmetries drive every decision in this module:

- **The request's work unit is modality-specific, not token-generic.** A text request's cost is dominated by output tokens. A VLM request's cost is dominated by *input* visual tokens (a single high-resolution image can expand to thousands of them before the model sees text). A diffusion request's cost is *denoising steps* multiplied by UNet / DiT forward passes — there are no output tokens at all. A streaming ASR request's cost is *audio seconds* flowing in. A reasoning request has a *hidden token count* that dwarfs the visible one. If the SLO vocabulary stays "P99 TTFT in seconds," it describes none of them well. Chapter 01 and chapter 02 rename the axes per shape.
- **The batching dimension changes per shape.** Text batching batches sequences along the sequence-length axis. Diffusion batching batches *prompts* along the batch axis for a shared UNet step. ASR streams batch *audio chunks* within fixed-size time windows. Agentic traffic can't be batched at the request level at all — each session is a slow conversation with the batcher. A single scheduler cannot optimise all four; chapters 02, 03, and 05 name the per-shape batching vocabulary.
- **The latency SLO breaks into two different budgets per shape.** For VLM: *image-preprocess time* plus *text-generation time*. For diffusion: *step time × step count* plus *VAE decode*. For ASR: *streaming chunk latency* and *final-transcript latency* as separate budgets. For TTS: *time to first audio frame* and *audio-render drift*. For reasoning: *think time* (hidden) and *answer time* (visible), and the user-visible waiting experience depends on whether you stream the reasoning or hide it. Each chapter names the two budgets its shape forces.
- **On-device is a real build-time alternative, not just an anti-pattern.** For a chat UX in a product with a strong privacy brand (health, finance, personal assistants), running a 3B-class model on the user's phone via llama.cpp / MLX / ExecuTorch is operationally cheaper than running a 70B-class model on a shared GPU — zero marginal cost per request, zero network-latency floor, offline by default. The inference engineer is the person who decides *whether to ship the inference at all*, and chapter 06 teaches the decision.

Those four asymmetries also set the chapter order: vision-language first (01, the modality most likely to land in your 2026 queue), diffusion (02, the next most likely), streaming speech (03, the one that most deeply bends the SSE discipline from module 111), reasoning (04, the shape currently most in flux among frontier model families), agentic (05, the shape that most changes the batcher's assumptions), and the server-vs-edge decision that closes the module (06).

## Boundary against the model-training and research tracks

This module is a *serving* module. It cares about how an already-trained VLM / diffusion / ASR / reasoning / agentic model is run in production. It does **not** teach:

- How a VLM's vision encoder is architected (`ai-infra-ml-platform` for model-registry, specialist vision / multimodal training tracks for architecture).
- How a diffusion model is trained or distilled (specialist generative-modelling tracks).
- How ASR tokenizers / acoustic models are built (specialist speech-processing tracks).
- How a reasoning model's chain-of-thought is trained (specialist reasoning-training literature).
- How an agent's prompt / policy is designed (`llm-application-developer` at L25).

If your diagnosis lands on *"the model's accuracy is wrong"* or *"the agent's policy loops"*, that is the training / application-layer peer. If it lands on *"the serving replica OOMs when the user uploads 12 images"*, *"the diffusion scheduler is set wrong for our latency SLO"*, *"the TTS stream stutters because our WebSocket framer is wrong"*, or *"we should ship this feature on-device"* — that is this module.

## Chapters

1. [**VLM Serving — Image Preprocessing, Visual-Token KV, Per-Image Budget, Variable-Image-Count Batching**](01-vlm-serving.md) — the VLM request as a mixed modality (image parts plus text parts), the image-preprocess stage (decode, normalise, resize, patchify) and where it runs (ingress vs. engine), the visual-token expansion ratio (an image is worth N visual tokens in the model's context — N depends on the encoder and the detail setting), the visual-token KV cache as a prefix-cache specialisation, the per-image token budget that bounds the worst-case request, and the batcher behaviour across requests with 0 / 1 / 3 / 12 images — admission, padding, and preempt policy.
2. [**Diffusion Serving — Steps, Schedulers, Denoising Batching, VAE Cost**](02-diffusion-serving.md) — the diffusion request as a denoising loop (noise → image / video / 3D), the step-count knob (50-step DDIM vs. 25-step DPM-Solver vs. 4-step LCM) as the dominant latency lever, the scheduler choice with its quality implications, the batch-along-prompt pattern that amortises the UNet / DiT step across concurrent requests, the VAE encode / decode as a separate GPU cost line, and the storage / egress piece for the output artefact (image blob to S3 vs. streamed to client).
3. [**Streaming Speech Serving — ASR, TTS, Chunking, Barge-In**](03-streaming-speech.md) — ASR streaming decode with partial-hypothesis emission, chunk sizing (the trade-off between finalization latency and WER), TTS streamed audio with time-to-first-audio-frame as the primary SLO, the audio framing on the wire (chunked HTTP, WebSocket, WebRTC), endpoint detection, and the barge-in semantics that cancel an in-flight TTS when the user interrupts (and the full-duplex state machine on the server to make that correct).
4. [**Reasoning-Model Serving — Think Traces, Budget Caps, Interruptible Decoding, Reasoning Channels**](04-reasoning-model-serving.md) — the reasoning request as *(hidden think tokens, visible answer tokens)*, the thinking-budget parameter and how different providers expose it (`reasoning.effort` / `max_completion_tokens` / native budget token-count), the UX choice of *stream the reasoning* vs. *hide it, stream only the answer*, the interruptible-decode plumbing so an operator or client can abort a stuck trace, and the structured reasoning-vs-answer channel split (OpenAI `/v1/responses` output items, Anthropic `thinking` content block) that keeps the client-side streaming UI correct.
5. [**Agentic Workloads at the Serving Edge — Long Sessions, Tool-Call-Heavy Shapes, Bursty Mixes**](05-agentic-workloads.md) — agentic traffic as a sequence of tool-interleaved short completions rather than one long completion, the per-session long-running state (open streams, idempotency keys, tool-call cursors), the latency-bursty vs. token-bursty traffic mix and what each does to the scheduler's batching assumptions, the ingress policy for tool-call round-trip timeout and session abandonment, and the observability axes that agentic workloads need (per-step latency, tool-success rate, session cost) that text-only SLOs do not expose.
6. [**Edge / Local / On-Device Inference — llama.cpp / MLX / MLC-LLM / ExecuTorch, Build-Time Decision**](06-edge-and-on-device.md) — a compare-point on the four dominant on-device runtimes (what each is, which platform / accelerator / model-format each targets, the quantization formats each consumes), the decision axes for server-vs-edge at build time (privacy, offline, cost per user, latency floor, model-footprint, update cadence, device-fragmentation), and the one-page RFC pattern that lets a product manager, a mobile engineering lead, and an inference engineer sign off on *where the inference physically runs*.

## Exercises

Each exercise carries a chapter into a reusable artefact — a VLM serving replica, a diffusion endpoint with a scheduler sweep, a speech streaming walkthrough, a reasoning-model deployment with think-budget controls, an agent-shaped load test, a build-time server-vs-edge RFC.

1. [**VLM Serving with Visual-Token Cache**](exercises/exercise-01-vlm-serving-with-visual-token-cache.md) — stand up a VLM replica, wire the image-preprocess stage, verify visual-token prefix-cache hits on image reuse, measure the per-image token expansion against the engine's documented behaviour, and prove the batcher stays stable under a mixed 0 / 1 / 3 / 12-image load.
2. [**Diffusion Serving with Scheduler Choice**](exercises/exercise-02-diffusion-serving-with-scheduler-choice.md) — serve a diffusion model, sweep step counts and schedulers (DDIM vs. DPM-Solver vs. Euler vs. LCM where available), measure the latency-vs-FID / latency-vs-CLIP-score curve, pick an operating point against a stated SLO, and publish the Pareto report.
3. [**Streaming ASR and TTS Walkthrough**](exercises/exercise-03-streaming-asr-and-tts-walkthrough.md) — stand up a streaming ASR endpoint (Whisper-class) and a streaming TTS endpoint, exercise them over WebSocket from a browser-style client, verify partial-hypothesis emission on ASR and time-to-first-audio-frame on TTS, implement barge-in cancellation, and publish the observability panel set.
4. [**Reasoning-Model Serving with Think Budget**](exercises/exercise-04-reasoning-model-serving-with-think-budget.md) — deploy a reasoning-capable model, wire the thinking-budget parameter through the ingress, implement interruptible decoding, expose the reasoning-vs-answer channel split, and prove the plumbing via a UX-shaped test (stream reasoning to a developer dashboard; stream only the answer to an end user).
5. [**Agentic Workload Shaped Benchmark**](exercises/exercise-05-agentic-workload-shaped-benchmark.md) — author a benchmark harness that plays agentic traffic (tool-interleaved, latency-bursty), measure the batcher's response (admission churn, preemption, per-step latency), compare against a text-only chat workload at the same QPS, and publish the agentic-vs-chat SLO delta.
6. [**Server-vs-Edge Decision Drill**](exercises/exercise-06-server-vs-edge-decision-drill.md) — take a hypothetical product feature (sketchable per team), build a one-page RFC that evaluates server-side vs. on-device inference across the chapter-06 axis set, reach a build-time recommendation, and defend it to a mobile engineering lead and a product manager (simulated or real).
