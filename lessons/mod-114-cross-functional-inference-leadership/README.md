# Module 114 — Cross-Functional Inference-Platform Leadership

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 14

Modules 101–113 built the serving stack, the deploy discipline, and the runbooks. This module is where the engineer who can run the stack becomes the engineer who can run the *program*. The weekly cadence. The build-vs-buy RFC. The vendor scorecard. The peer interfaces that keep the performance peer, the ML-platform peer, the eval peers, the SRE peer, and the security peer all moving at the same tempo. The career map above it all.

An inference-platform program at team scope is defined by written artefacts — charter, SLO contract, change calendar, runbook set, RFC, scorecard, peer contracts. This module is the authoring curriculum for those artefacts.

By the end of it you can:

- **Own an inference-platform program at team scope** — the weekly SLO-review ritual, the monthly change-calendar review, the quarterly migration roadmap, an on-call rotation and paging matrix shaped for inference failure modes (not web failure modes), a change calendar that respects consumer-track freezes and peer dependencies, and migration plans that preserve rollback and name peer deliverables.
- **Author an inference-platform build-vs-buy RFC** — the three-option frame (self-host vLLM / SGLang / TensorRT-LLM / NVIDIA Dynamo; managed inference at Fireworks / Together / Baseten / Modal / NVIDIA NIM; hybrid), the workload-class decomposition, a defensible total-cost-of-ownership model (hardware + underutilised + warm pool + storage + observability + egress + licences + people + on-call + opportunity + exit, for self-host; usage + overage buffer + commits + transit + observability-integration + security + integration-people + incident-ownership + discount-erosion + exit, for managed), a risk register with likelihood / impact / owner / mitigation, a migration path with explicit rollback branches, and the triggers that reverse the decision.
- **Run a vendor eval and produce a defensible scorecard** — five axes (SLA, price, feature parity, exit cost, data boundary) each decomposed into sub-dimensions and scored against evidence (not vendor marketing), per-vendor detail pages, a sponsor-readable summary comparison, and a decision cover memo.
- **Author the interface contract with the performance peer** — a ticket template (required and optional fields; the `rule_outs_performed` list that cuts off non-kernel tickets early), negotiated response SLAs, five return shapes, a kernel-regression ledger reviewed quarterly, reverse tickets as a first-class pattern, and a shared on-call escalation for P0.
- **Author the interface contracts with the ML-platform (L30), eval (L30 × 2), SRE (L30), and security (L35) peers** — the five-part contract shape (boundary statement, mutual deliverables, ticket template, response SLA, shared incident path), applied once per peer, with the common failure modes named.
- **Position the inference-engineer career trajectory** — four plausible next steps (specialism-deeper, scope-wider, craft-cross, people), the load-bearing certifications (Kubernetes CKA / CKAD, one cloud-provider ML cert, NVIDIA DLI inference-aligned courses), the open-source engine contribution ladder (bug-fix → small-feature → recurring → committer → core), and a one-page quarterly career plan.

The weekly SLO review (chapter 01) reads module 110's dashboard and the module 113 chapter 01 deploy events on one page. The build-vs-buy RFC (chapter 02) references module 110 chapter 04's cost arithmetic and the module 109 fleet-shape as inputs. ## The core framing

The inference-platform program at L35 is a *written system*. If any of its load-bearing artefacts is missing or stale, the program is one incident away from chaos. Five artefacts carry most of the weight:

- **The weekly SLO review** — the central ritual; one dashboard URL as the agenda; one ticket out of every unresolved item.
- **The build-vs-buy RFC** — the decomposition, the TCO model, the risk register, the migration path; signed by platform lead, sponsor, and the peer leads whose work the decision touches.
- **The vendor scorecard** — five axes against evidence from *your* traffic, not vendor benchmarks; three pages (per-vendor detail, summary comparison, decision cover memo).
- **The peer interface contracts** — one per peer; five-part shape (boundary, deliverables, ticket template, SLA, shared incident path); signed and reviewed quarterly.
- **The career plan** — the engineer's own one-page document; specialism-deeper vs. scope-wider vs. craft-cross vs. people; reviewed quarterly.

Each chapter below authors one of these artefacts — except the peer interfaces, which are the subject of chapters 04 and 05 because their density justifies two chapters.

## Boundary against module 113

Module 113 owns the *mechanics of change inside a deploy*. This module owns the *program the deploys happen inside*. The split, concretely:

- Module 113 chapter 01 defines the canary ramp and auto-rollback; module 114 chapter 01 schedules when canaries run against the consumer-track freezes.
- Module 113 chapter 05 defines the eval-gate contract with the two eval peers; module 114 chapter 05 situates that contract in the full peer-interface program and names the quarterly review.
- Module 113 chapter 06 defines the deprecation runbook; module 114 chapter 01 picks the slot on the migration roadmap and chapter 06 names the career-portfolio value of having authored several.

Rule of thumb: *"when does this specific change happen"* → module 113. *"when does any change happen, and against what peer dependencies, and whose program commits to it"* → this module.

## Boundary against the L40 architect / team-lead tracks

The architect track at L40 (`ai-infra-architect`) owns *cross-stack architecture at team-of-teams scope*. The team-lead track at L40 (`ai-infra-team-lead`) owns *people management*. This module owns the inference-platform program at *team scope*, as an IC role; it does not cover the architecture-across-many-platforms conversation (that is L40 architect) or the hiring / performance-review / engineering-management conversation (that is L40 team lead). Chapter 06 positions the hand-off to each.

## Exercises

Each exercise carries a chapter into a reusable artefact — a cadence document, an RFC, a scorecard, two sets of peer contracts, and a career plan.

1. [**Platform Program Cadence and Ritual Authoring**](exercises/exercise-01-platform-program-cadence-and-ritual-authoring.md) — author the four cadence artefacts for your fleet (charter, SLO contract pointer, change calendar, runbook set + on-call rotation), run (or dry-run) a weekly SLO review, publish a monthly change-calendar view, draft a quarterly migration roadmap with one migration plan at full detail, and document the on-call paging matrix.
2. [**Build-vs-Buy RFC Authoring**](exercises/exercise-02-build-vs-buy-rfc-authoring.md) — write a full build-vs-buy RFC for a plausible decision facing your fleet (if your fleet is simulated, pick a realistic hypothetical), including workload decomposition, full TCO models for each option, a risk register, a migration path, and the triggers that would reverse it.
3. [**Vendor Eval Scorecard Drill**](exercises/exercise-03-vendor-eval-scorecard-drill.md) — run a full vendor evaluation across at least three real vendors against the five-axis rubric, including a benchmark on your (or a plausible proxy) traffic sample, publish the three-page artefact, and defend the weighting choices.
4. [**Performance Peer Interface Contract**](exercises/exercise-04-performance-peer-interface-contract.md) — draft the ticket template, response SLA table, return-shape taxonomy, and kernel-regression ledger for the interface with your performance peer; file or dry-run three tickets (two in, one reverse); record a worked example with the ledger entry.
5. [**Cross-Peer Interface Contracts**](exercises/exercise-05-cross-peer-interface-contracts.md) — draft the four remaining peer-interface contracts (ML platform, two eval peers, SRE, security) using the five-part shape, get sign-off (simulated if peers are not available), and publish a cross-peer cadence that covers them weekly and quarterly.
6. [**Career Trajectory and Cert Portfolio**](exercises/exercise-06-career-trajectory-and-cert-portfolio.md) — write your own one-page career plan against the chapter 06 template, pick a 12-month certification sequence, commit to an open-source engine and three to five realistic first contributions, and schedule the quarterly review of the plan.
