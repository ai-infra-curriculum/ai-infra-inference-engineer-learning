# Module 106 — Multi-Model, Multi-Tenant, and Multi-Adapter Serving

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 16

Modules 102–105 served one model per fleet, held one adapter per worker, and admitted one tenant's traffic at a time. A production inference platform does none of those things. The fleet holds hundreds-to-thousands of LoRA adapters, co-locates a handful of small models on each GPU, and routes every request through a cost-aware policy that can pick a cheap self-hosted model, an expensive self-hosted model, or an external provider depending on budget and difficulty — all while keeping tenant A's noisy workload off tenant B's P99. This module is the serving-side plumbing for that reality.

By the end of it you can:

- Deploy **multi-LoRA serving at thousand-adapter scale** using the S-LoRA / Punica abstractions implemented in vLLM and SGLang — adapter registry, lazy load, batch-level adapter switching, per-adapter memory footprint, and the kernel-level batched LoRA GEMM those engines dispatch into.
- Deploy **multi-model co-location on a single GPU** for small / cheap models using the engine-level primitives (vLLM / SGLang multi-model servers, Triton model-ensemble), the hardware-level primitives (MIG hard partitions, MPS soft sharing, Kubernetes DRA), and reason about the latency / throughput / isolation trade-off between them.
- Design a **cost-aware request router** — cheap-model-first with escalation on confidence drop, per-request budget cap, per-tenant quota, and provider fallback across self-hosted → Fireworks → Together → Baseten → the model vendors' direct APIs. The router shape mirrors what LiteLLM exposes, but it lives on *your* server, not inside the application.
- Deploy a **dynamic weight-loader** for the long tail of adapters that cannot stay resident — eviction policy, cold-start cost accounting, warm-set sizing, pin-set for latency-critical adapters.
- Author a **multi-tenant isolation contract** — per-tenant SLO, noisy-neighbour mitigation, token-rate limits, data-boundary respect for KV / prefix sharing (which composes with module 104's cross-tenant sharing policy).
- Cite the **boundary to `llm-application-developer`** (consumer peer, level 25) on the application-side provider SDK — this module owns the *server-side* router; the application-side LiteLLM / OpenAI SDK is theirs.

> **Prerequisites:** [Module 101](../mod-101-inference-engineering-position/README.md) (vocabulary — LoRA, PEFT, provider fallback, multi-tenant terminology), [Module 102](../mod-102-inference-engine-internals/README.md) (vLLM / SGLang / TRT-LLM internals and where the adapter-manager hooks sit), [Module 103](../mod-103-request-scheduling-and-batching/README.md) (continuous batching — the batched LoRA kernel is a scheduler-level concern), [Module 104](../mod-104-kv-cache-management/README.md) (cross-tenant prefix-sharing data boundary — this module composes with that), and [Module 105](../mod-105-quantization-and-model-ops/README.md) (weight-loader and in-flight swap mechanics — this module reuses the swap primitive).

## Boundary against `ai-infra-performance`

The S-LoRA / Punica side has two faces. One is the **batched LoRA GEMM kernel** itself — Punica's segmented matmul, S-LoRA's unified paging over heterogeneous ranks, SGEMM-with-adapter-index — which the peer at [`ai-infra-performance`](https://github.com/ai-infra-curriculum/ai-infra-performance-learning) owns. If your diagnosis lands on "the batched LoRA kernel's utilisation is below the specialist's benchmark" or "the segmented matmul's warp-level reduction is leaving flops on the table," the fix is a `.cu` / `.cuh` / Triton-DSL / CUTLASS edit — route to the performance peer.

The other face is the **production operation**: adapter registry schema, lazy load lifecycle, batch admission with heterogeneous adapters, eviction and warm-set sizing, cross-tenant isolation, cost-aware routing on top. That face is this module. The deliverable here is a registry, a config, a router, a policy, and a runbook — not a kernel edit.

Rule of thumb: *if the fix is to a kernel source file (`.cu` / `.cuh` / Triton kernel / CUTLASS epilogue) or to a batched-GEMM data layout, that is the performance peer. If the fix is to an adapter-registry entry, an eviction knob, a router policy, a tenant quota, or an isolation contract, that is this module.*

## Boundary against `llm-application-developer`

The AI Engineering family's [`llm-application-developer`](https://github.com/ai-engineering-curriculum/llm-application-developer-learning) track (consumer peer, level 25) owns the **application-side** provider SDK — the LiteLLM client, the OpenAI SDK, the retry/timeout/circuit-breaker code that an *application* uses when it calls a model API. That shape of code lives in a web app, a batch pipeline, or an agent — not on the serving fleet.

This module owns the **server-side** cost-aware router — a service that sits in front of your inference fleet, accepts OpenAI-compatible traffic, decides which model to route each request to, enforces per-tenant quotas, and composes self-hosted and external providers behind one endpoint. From the application's point of view this looks like any other API; from the fleet's point of view it is the admission and policy layer.

Rule of thumb: *if the code is linked into an application process making outbound calls to a model API, that is the application-developer peer. If the code is a service accepting inbound requests and deciding which model to serve them from, that is this module.*

## Boundary against module 104

Module 104 owns the KV cache as a runtime object — PagedAttention, RadixAttention, prefix sharing, tiered stores, and the cross-tenant KV sharing policy. This module composes with that policy on the multi-tenant side: when a request arrives tagged with a tenant, the router here decides *which* fleet it lands on; the chapter-05 isolation contract here decides *whether* that tenant can share a prefix cache with another tenant on that fleet. The data-boundary semantics live in 104; the tenant model and the enforcement live here.

## Boundary against module 105

Module 105 owns the in-flight *model* swap primitive (dual-load, drain, blue-green, in-flight weight reload). This module reuses that primitive for the *adapter-level* swap — loading and evicting adapters at runtime without disrupting in-flight requests. The structural problem is the same (bytes-in-HBM must change without dropping requests), but at adapter scale the knobs are different (adapters are MiB, not GiB; swaps are per-second, not per-day).

## Boundary against module 113

Module 113 owns the production-rollout mechanics (canary, shadow, response-diff, auto-rollback) as a general discipline. This module owns the serving-side mechanics for one specific category of change — *routing-policy* changes (new provider added, cost cap tightened, cheap-model-first threshold adjusted) and *adapter-fleet* changes (adapter promoted from staging to production, adapter decommissioned). 113 is the rollout framework; 106 provides the primitives that framework ramps.

## Exercises

The exercises carry each chapter into a hands-on drill you keep as a reusable artefact for the rest of the track:

1. [**Deploy Multi-LoRA with the S-LoRA Pattern**](exercises/exercise-01-deploy-multi-lora-with-s-lora-pattern.md) — serve one base model with twenty or more LoRA adapters on a single GPU; measure per-adapter cold-start latency, batched-adapter throughput, and HBM footprint vs. the "one base model per adapter" baseline; publish the adapter-registry schema you fed the engine.
2. [**Small-Model Co-location on a Single GPU**](exercises/exercise-02-small-model-co-location-on-single-gpu.md) — co-locate two or more small models on one GPU via each of the three mechanisms (engine-level, MIG, MPS); measure the TTFT / throughput impact of a noisy second workload under each; publish the trade-off table.
3. [**Cost-Aware Router Authoring with LiteLLM Shape**](exercises/exercise-03-cost-aware-router-authoring-with-litellm-shape.md) — stand up a router in front of your fleet (self-hosted + at least one external provider); implement cheap-model-first with escalation, per-request budget, per-tenant quota, and provider fallback; drive a mixed workload and publish the cost-per-1k-tokens, escalation-rate, and tenant-SLO numbers.
4. [**Dynamic Adapter Loader with Eviction**](exercises/exercise-04-dynamic-adapter-loader-with-eviction.md) — simulate a long-tail adapter workload (50–200 adapters, Zipfian popularity); size the warm set; implement an eviction policy; measure cold-start-latency, hit-rate, and HBM footprint; defend the warm-set size against the measured workload.
5. [**Multi-Tenant Isolation Contract Drill**](exercises/exercise-05-multi-tenant-isolation-contract-drill.md) — author a contract for two tenants with different SLOs; simulate a noisy-neighbour scenario; show the isolation holds (noisy tenant does not blow quiet tenant's P99); run a prefix-sharing audit against the module-104 boundary; produce the signed contract and the audit log.
