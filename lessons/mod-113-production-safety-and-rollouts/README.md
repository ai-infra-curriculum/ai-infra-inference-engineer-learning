# Module 113 — Production Safety, Rollouts, and Incident Response for Inference

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 14

Modules 102–112 built the serving stack and the methodology to measure it. This module is where the stack meets *change* — a new engine version, a re-quantised model, a scheduler-flag tweak, a draft-model promotion, a new GPU SKU, a routed deprecation. Every one of those changes is also the shape of every past outage this track has to prevent. The deploy ritual, the runbook set, the incident response, and the hand-off contracts with the eval peers are what turn "we have an SLO" into "we honour the SLO when things change."

The craft here is specifically *inference-flavoured*. Canary on a stateless web service means "route 1 % of traffic, watch error rate, promote." Canary on an inference service means "route 1 % of traffic, run response diffs across the old and new model under a semantic-equivalence tolerance, watch TTFT / TPOT / cache-hit / preemption deltas, roll back on an SLO burn-rate alert that is counted in tokens not requests." Blue-green on a stateless service means "cut the load balancer." Blue-green on a 70B replica means "we can't dual-load the model on this node; draining has to come first; the cutover has to be atomic across streaming sessions mid-flight." The runbooks for "pod is restarting" don't cover "cache-hit cliff," "preemption spike," or "silent accuracy regression." This module writes the version that does.

By the end of it you can:

- **Deploy canary and shadow-traffic rollouts for an inference fleet** — response diffing with semantic-equivalence tolerance (not byte-equality, which never holds for a stochastic decoder), the canary-weight ramp (1 % → 5 % → 25 % → 100 %) with promotion gates at each step, SLO-based auto-rollback on burn-rate alerts over the inference axis set (TTFT, TPOT, cache-hit, preemption, admission-reject), and the shadow-traffic pattern for changes where response-diff is the only honest signal (quantisation change, engine upgrade, speculative-decoding promotion).
- **Deploy blue-green and in-flight model swap for large models** — the dual-load constraint (you often can't fit old + new on one node for a 70B+ model), the drain-and-swap pattern that respects streaming sessions, the atomic routing cutover that doesn't break mid-stream, the `X-Model-Version` header that gives clients and dashboards a clean axis to attribute regressions to, and the rollback-time budget that constrains how fast the cutover must be reversible.
- **Author inference-specific runbooks** — a single runbook template the team shares, and the authored top-ten set: *TTFT regression*, *cache-hit cliff*, *preemption spike*, *silent accuracy regression / output drift*, *NCCL hang*, *GPU driver / XID / ECC error*, *worker crash loop*, *admission-reject flood*, *KV OOM*, *streaming-close storm*. Each runbook is structured so the on-call engineer who has never seen the incident before can still bisect in minutes.
- **Run inference incident response** — the triage pattern specific to inference (bisect against the axis set from module 110, not against a single E2E percentile), the RCA assembly from traces + metric overlays + model-version diffs + config diffs + deploy-event timeline, the post-mortem artefact in the shape the SRE peer's (L30) methodology expects, and the permanent regression-fixture back-feed that turns "we fixed the incident" into "this incident cannot recur silently."
- **Author an eval-gate contract with the two upstream eval peers** — `ai-eval-engineer` (peer, L30, AI Engineering family) for application-layer evals, and `model-evaluation-engineer` (peer, L30, ML Engineering family) for benchmark / capability evals. The contract names *what passes blocks promotion*, *what fails rolls back*, *what degrades gracefully with a feature-flagged client-side fallback*, and *who signs what by when*.
- **Author a model-deprecation runbook** — the grace period (not days, not years — the right length for this product), the migration guide for the consumer tracks (`llm-application-developer`, `rag-engineer`, `applied-ai-engineer` at L25), the deprecation-warning header on live responses, the decommission timeline with explicit cutover and rollback-exit points, and the capacity-reclaim step that recovers the GPU budget.

> **Prerequisites:** [Module 102](../mod-102-inference-engine-internals/README.md) (engine debug surface — the runbooks dispatch to engine-specific primitives), [Module 103](../mod-103-request-scheduling-and-batching/README.md) (scheduler knobs — preemption spike and admission-reject flood runbooks operate on these), [Module 104](../mod-104-kv-cache-management/README.md) (cache-hit cliff and KV OOM runbooks live here), [Module 105](../mod-105-quantization-and-model-ops/README.md) (the accuracy-regression gate — chapter 05 specialises its release contract), [Module 107](../mod-107-distributed-inference-topologies/README.md) (NCCL hang runbook), [Module 109](../mod-109-autoscaling-fleet-and-resilience/README.md) (worker crash loop and preemption interact with autoscaling), [Module 110](../mod-110-observability-slo-and-cost/README.md) (the SLO and axis set this module's auto-rollback and runbooks consume), [Module 111](../mod-111-inference-api-and-protocols/README.md) (the `X-Model-Version` header, the streaming-session semantics that blue-green must preserve). The L30 `ai-infra-sre` track covers general SRE methodology (SLI / SLO math, incident command, blameless post-mortem) — this module consumes that methodology for inference-specific signals and names the hand-off explicitly.

## The core framing

Inference rollouts and inference incident response look like SRE and *are not*. Four asymmetries drive every design decision in this module:

- **A model is not a code change; you cannot diff it.** A code deploy produces a reviewable patch and deterministic unit tests. A model swap replaces a 70-billion-parameter tensor-value function with a different one. Byte-equality of responses never holds — the decoder is stochastic even at `temperature=0` due to non-associative FP, batching effects, and kernel non-determinism. Response diffing needs a *semantic equivalence* tolerance, and the acceptance threshold is a product decision — not a code-review decision. Chapter 01 names the tolerance vocabulary.
- **The request you're canarying is a token stream, not a one-shot call.** A 25-second chat completion that started on the old model and finished on the new one is not a comparable response. Cutover cannot happen mid-stream; rollout must respect session boundaries; shadow traffic must copy input fairly and discard output without affecting the primary path. Chapter 01 and chapter 02 name the stream-respecting primitives.
- **The GPU is the scarce resource and dual-load has a cost.** Blue-green on a stateless web service runs green at 100 % of peak alongside blue — twice the fleet for a few minutes. Blue-green on a fleet of 64 H100 replicas serving a 70B model at `TP=8` is either "we provisioned a second fleet" (expensive) or "we drain and swap in place" (slower, but the only option on tight GPU budgets). Chapter 02 names which pattern applies when.
- **Silent accuracy regressions are the inference equivalent of data corruption.** A code deploy that returns the wrong HTTP status fails a smoke test in ten seconds. A quantisation change that drops task accuracy by 2 % at long context passes every latency SLO, passes the engine health check, passes the response-length distribution check, and ships to 100 % of users — until a product manager notices the retention curve bending. The eval gate (chapter 05) and the silent-drift runbook (chapter 03) exist because this failure mode is the one SRE methodology does not describe.

Those four asymmetries also set the chapter order: canary + shadow + response-diff first (01, the deploy mechanism), blue-green and model-swap second (02, the pattern for the subset of changes that can't canary cleanly), runbooks third (03, the on-call surface), incident response fourth (04, the glue across the axis set from module 110 and the deploy events from 01–02), eval-gate fifth (05, the upstream contract that gates promotion), and deprecation sixth (06, the downstream contract that gates removal).

## Boundary against `ai-infra-sre` (peer, level 30)

The SRE **methodology primitives** — definition of SLI / SLO / error budget, multi-window multi-burn-rate alerting, incident-command role structure (commander, scribe, communicator), blameless post-mortem framing, action-item discipline, on-call rotation design — live at [`ai-infra-sre-learning`](https://github.com/ai-infra-curriculum/ai-infra-sre-learning). If your question is *"what is the right burn-rate ratio for a 30-day window"* or *"how do I run incident command for a multi-team incident"*, that is the L30 track.

The **inference-specific extensions** are this module:

- The canary rollout vocabulary specialised for a stochastic decoder (response diffing, semantic-equivalence tolerance, per-class SLO gating, token-budget-aware ramp).
- The blue-green pattern specialised for GPU-resident, memory-expensive models (dual-load constraint, drain-and-swap, atomic streaming-session cutover).
- The runbook set specialised for inference failure modes (cache-hit cliff, preemption spike, NCCL hang, silent output drift) that generic SRE runbooks do not cover.
- The RCA assembly that correlates the inference axis set (TTFT / TPOT / ITL / cache-hit / preemption / DCGM / NCCL) with model-version and config diffs on one timeline.
- The eval-gate contract specialised for inference artefacts (model weights, quantisation configs, speculative-decoding draft-target pairs, LoRA adapters) and the two peer tracks that produce the evals.
- The deprecation runbook specialised for an inference artefact's consumer surface (API model names, routing rules, feature-flagged clients, capacity reclaim).

Rule of thumb: *if the question is "how do we do deploy / incident / post-mortem here," that is the L30 peer. If the question is "how do we do deploy / incident / post-mortem here because the artefact is a model, the regression is semantic, the signal is tokens, and the resource is GPU," that is this module.*

## Boundary against module 110

Module 110 owns the steady-state methodology — the SLO contract, the dashboard, the cost accounting. This module owns the deploy-time and incident-time discipline — the canary ramp, the auto-rollback, the runbook, the RCA, the post-mortem. The split: 110 decides *the contract and the measurement*; 113 decides *the deploy ritual and the incident choreography*.

Concretely: the burn-rate alert fires on an SLO authored in module 110; the *auto-rollback action* on that alert is authored here. The latency decomposition panel is built in module 110; the *runbook that bisects against it during a TTFT regression* is authored here. The DCGM / NCCL axis set is defined in module 110; the *NCCL-hang runbook and the ECC-error incident procedure* are authored here.

## Boundary against module 114 (leadership)

Module 114 owns the program — the cadence, the change calendar, the build-vs-buy decision, the vendor eval, the roadmap. This module owns the *mechanics of change inside a cadence step*. If the question is *"when does our team deploy this quarter and what gates it,"* that is 114. If the question is *"when this specific change goes through the gate, what happens token-by-token,"* that is here.

2. [**Blue-Green and In-Flight Model Swap — Dual-Load, Drain-and-Swap, Atomic Cutover, Model-Version Header**](02-blue-green-and-model-swap.md) — the blue-green pattern when GPU budget allows a full second fleet (the simple case) and the drain-and-swap pattern when it does not (the common case for 70B+ models), the dual-load constraint named per hardware class (how much HBM headroom you need to overlap two versions on one replica — sometimes none), the atomic routing cutover that respects streaming sessions (requests in-flight on blue finish on blue; new requests go green; the LB stops accepting mid-stream cuts), the `X-Model-Version` response header that gives clients and dashboards a clean attribution axis, and the rollback-time budget that constrains how fast the cutover must be reversible under an SLO burn-rate page.

4. [**Incident Response and RCA for Inference — Triage, Overlays, Version Diffs, Post-Mortem, Fixture Back-Feed**](04-incident-response-and-rca.md) — the inference-shaped triage pattern (the chapter-01 axis set bisection from module 110 is step zero, not step four), the RCA artefact that overlays traces + metric time-series + model-version and config diffs + deploy-event timeline on one page, the post-mortem template that satisfies the SRE peer's methodology for an inference-shaped incident, and the permanent regression-fixture back-feed — the step that turns *"we fixed the incident"* into *"this incident cannot recur silently"* by adding the failure case to the eval set (chapter 05) and / or the canary acceptance gate (chapter 01).
5. [**The Eval-Gate Contract with `ai-eval-engineer` and `model-evaluation-engineer`**](05-eval-gate-contract.md) — the two upstream peers that produce the evals that gate inference promotion (`ai-eval-engineer` at L30 in the AI Engineering family for application-layer evals; `model-evaluation-engineer` at L30 in the ML Engineering family for capability / benchmark evals), the contract fields (*what passes blocks promotion*, *what fails triggers rollback*, *what degrades gracefully with a client-side feature-flag fallback*, *who owns the fixture back-feed from chapter 04*), the division of ownership on the fixture set (benchmark fidelity → the ML-eval peer; application behaviour → the AI-eval peer; post-incident fixtures → this role), and the on-call interaction pattern when an eval regresses outside a release window.
6. [**Model-Deprecation Runbook — Grace Period, Migration Guide, Decommission Timeline**](06-model-deprecation-runbook.md) — the deprecation decision (what triggers it — usage decay, replacement availability, cost, compliance), the grace period calibrated against the consumer tracks' release cadence (not weeks for a team on a monthly release train; not months for an experimental model), the deprecation warning on live responses (header / response-metadata pattern), the migration guide written for the consumer tracks (`llm-application-developer`, `rag-engineer`, `applied-ai-engineer` at L25) with a replacement model recommendation and a diff of expected behaviour changes, the decommission timeline with explicit cutover-rollback-exit points, and the capacity-reclaim step that returns GPU budget to the fleet.

## Exercises

Each exercise carries a chapter into a reusable artefact — a canary harness, a blue-green walkthrough, a runbook set, a mock incident with RCA and post-mortem, an eval-gate contract draft, a deprecation runbook.

1. [**Canary with Response Diffing and Auto-Rollback**](exercises/exercise-01-canary-with-response-diffing-and-auto-rollback.md) — build a canary harness that routes a small fraction of traffic to a candidate model version, scores the response-diff against a semantic-equivalence tolerance you defend in writing, wires an SLO-based auto-rollback on burn-rate alerts across the inference axis set, and demonstrates a promote-and-rollback cycle end-to-end.
2. [**Blue-Green Model Swap Walkthrough**](exercises/exercise-02-blue-green-model-swap-walkthrough.md) — perform a blue-green model swap on a representative replica fleet, respect in-flight streaming sessions, prove the atomic cutover via the `X-Model-Version` header on responses, measure the rollback-time budget, and document the dual-load decision for your fleet's hardware.
3. [**Inference Runbook Authoring — Top Ten**](exercises/exercise-03-inference-runbook-authoring-top-ten.md) — author the ten chapter-03 runbooks against the shared template for your fleet's engines / hardware / SLOs, link each to the module-110 axis and the originating module's debug surface, and dry-run each against an induced or recorded incident so the on-call sheet is live-tested before it is read at 2 AM.
4. [**Mock Incident — RCA and Post-Mortem**](exercises/exercise-04-mock-incident-rca-and-postmortem.md) — induce or replay a recorded inference regression, run the triage pattern from chapter 04, assemble the RCA artefact with overlays and diffs, write the blameless post-mortem, and back-feed the regression fixture into the eval set and the canary acceptance gate.
5. [**Eval-Gate Contract with Peer Tracks**](exercises/exercise-05-eval-gate-contract-with-peer-tracks.md) — draft the eval-gate contract from chapter 05 as a real document that your fleet's `ai-eval-engineer` and `model-evaluation-engineer` peers would sign off on (simulated if you don't have those peers available), negotiate the pass / fail / degrade thresholds against two or more model promotions, and publish the contract with a dispute-resolution path.
6. [**Model-Deprecation Runbook**](exercises/exercise-06-model-deprecation-runbook.md) — pick a model currently served on your fleet (or a plausible stand-in) that is a candidate for deprecation, author the full deprecation runbook from chapter 06 (grace period, deprecation headers, consumer migration guide, decommission timeline, capacity-reclaim), socialise the migration guide with a simulated consumer-peer review, and publish the artefact.
