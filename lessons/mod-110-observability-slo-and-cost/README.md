# Module 110 — Inference Observability, SLO Engineering, and Cost per Inference

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 16

Modules 102–109 made a replica fast, made a fleet elastic, and made the GPUs resilient. This module answers the next three questions: *is the fleet meeting its promise, is the fleet worth the money, and does the business care*. All three are observability questions, but the standard SRE / APM toolkit (RED metrics on a Flask app, request-count-based error budgets, `/metrics` for a stateless service) does not describe inference workloads well. A single request is not atomic; it emits tokens over seconds; TTFT and TPOT are negotiated as separate SLOs; the GPU is the most expensive line item on the bill and never fully utilised; the cache hit is a cost multiplier. This module teaches the inference-specific extensions.

By the end of it you can:

- **Instrument an inference fleet with the right axis set** — TTFT, TPOT, ITL (inter-token latency), E2E latency, cache-hit rate, preemption rate, admission-reject rate, prefill-decode mix, GPU utilisation (via DCGM — SM active, HBM used, NVLink / PCIe traffic, power), SM activity, memory pressure, NCCL time — and reason about which to alert on, which to dashboard, and which to retain as a sampled trace.
- **Design SLOs shaped for inference workloads** — latency SLOs defined per workload class (chat, code, batch, long-context, agent / tool-use), an availability SLO that counts tokens served not just requests completed, a cache-hit SLO where the cache is a cost SLO's dependency, a cost SLO expressed in `$ per 1M tokens`, and error budgets at per-token granularity rather than per-request.
- **Build a Prometheus / Grafana / OpenTelemetry stack for inference** — DCGM-exporter wired to the Prometheus Operator, engine-exposed metrics scraped with correct label cardinality, request tracing with OTel spans that cover admission → prefill → decode → stream-close, and a log-sampling strategy that survives 10k QPS without burning the cluster's logging budget.
- **Compute cost per 1M input tokens and cost per 1M output tokens at operator depth** — the amortised GPU-hour, the utilisation adjustment (idle time still bills), the prefix-cache credit (served from cache ≠ served for free, but close), the speculative-decoding credit (acceptance rate changes effective TPOT and therefore cost per token), and the cost-per-request SLO you set once you have the per-token numbers.
- **Draw the throughput-vs-latency Pareto curve** for a stated model + fleet + traffic shape — the batch-size sweep, the TTFT-vs-TPOT trade-off, the goodput envelope (throughput at or below the latency SLO), and the argument that defends your current Pareto point against a product manager's "can we just double throughput."
- **Tie inference metrics into business metrics** — product KPI delta per TTFT millisecond improvement, cost per revenue token, latency-attributable churn, and the pattern that lets you answer *"is this optimisation worth the ask"* in a one-page memo rather than a six-week ticket.
- **Cite the boundary to [`ai-infra-sre`](https://github.com/ai-infra-curriculum/ai-infra-sre-learning) (peer, level 30)** — general SRE methodology (SLI / SLO / error-budget math, burn-rate alert design, incident command, postmortem discipline) lives there; this module adopts that methodology for inference-shaped signals and names the hand-off for cross-cutting SRE work.

## The core framing

Inference observability looks like service observability and *is not*. Three asymmetries drive every design decision in this module:

- **A request is not one event; it is a token stream.** A chat request may emit 500 tokens over 15 seconds. TTFT (time to first token) measures the admission / prefill critical path; TPOT (time per output token) measures the decode steady state; ITL (inter-token latency) measures jitter inside the decode stream. One request produces one histogram sample for TTFT, one TPOT distribution, and dozens of ITL samples. The SLO that treats the request as atomic ("P99 latency < 2 s") hides most of what matters. Chapter 01 names the axis set that keeps the signal.
- **The right error-budget unit is a token, not a request.** A fleet that serves 10k requests per second producing 500 tokens each is a fleet that serves 5M tokens per second. A 0.1 % latency SLO breach on *requests* is a 0.1 % breach on *tokens*, but a 0.1 % breach on *long-context* requests may be a 20 % breach on *long-context tokens*. Chapter 02 defines the per-token error budget, the burn-rate math on top of it, and the per-workload-class slicing that keeps a long-tail class from being masked by a chat-dominated denominator.
- **The GPU is the dominant line item and is never fully utilised.** DCGM reports `SM_ACTIVE` near 1.0 for a single-request prefill *and* for a saturated batch — the metric is "GPU is doing something," not "fleet is well-used." The economically meaningful utilisation is `tokens_per_gpu_hour`, and the economically meaningful cost is `$ per 1M tokens`, both of which require this module's accounting discipline. Chapter 04 builds the model; chapters 05 and 06 defend it.

Those three asymmetries also set the chapter order: the axis set first (01), the SLO methodology on top (02), the stack that produces the signal (03), the cost model that converts the signal into dollars (04), the Pareto curve that defends a point (05), the business-metric tie-in that justifies the ask (06), and the boundary to the SRE peer that keeps this module's scope honest (07).

## Boundary against `ai-infra-sre` (level 30)

The SRE **methodology primitives** — the definition of an SLI, the mechanics of SLO targets and error budgets, the multi-window multi-burn-rate alert pattern, incident command / commander-vs-scribe discipline, postmortem writing with blameless framing, on-call rotation and escalation design — live at [`ai-infra-sre-learning`](https://github.com/ai-infra-curriculum/ai-infra-sre-learning). If your diagnosis lands on *"what is the right burn-rate formula for a 30-day SLO window,"* *"how do we structure incident command for a cross-team incident,"* or *"what does a good postmortem look like"* — that is the L30 track's scope. Go there first.

The **inference-specific extensions** are this module:

- The axis set (TTFT, TPOT, ITL, cache-hit, preemption, admission-reject, prefill-decode mix, NCCL time, DCGM GPU metrics) that generic SRE methodology does not describe.
- The per-token error budget (not per-request) that the inference token-stream shape requires.
- The per-workload-class SLO slicing (chat vs. code vs. long-context vs. batch) that reflects how inference workloads actually diverge.
- The DCGM-exporter / engine-metrics wiring that is GPU-specific.
- The OTel span layout for a prefill-then-decode request that generic HTTP tracing does not model.
- The cost-per-1M-token accounting with prefix-cache and speculative-decoding credits.
- The throughput-vs-latency Pareto reasoning that is specific to the batched-attention regime.
- The business-metric tie-ins (TTFT ms → KPI, cost per revenue token) that convert inference engineering into product arguments.

Rule of thumb: *if the question is "how do we do SRE here," that is the L30 peer. If the question is "how do we do SRE here because the signal is tokens, the GPU is the cost, and the request is a stream," that is this module.*

Chapter 07 formalises the boundary with a mapping table, a hand-off list, and the three common cross-boundary mistakes.

## Boundary against modules 102, 103, 104, 107, 108, 109

The engine emits the metrics, the scheduler emits the queue counts, the KV allocator emits the cache rates, the parallelism topology emits the NCCL time, speculative decoding emits the acceptance rate, the autoscaler consumes the signals. Those are all upstream of this module. This module names:

- **Which signals to scrape** (chapter 01) — the inference axis set as a union of what every upstream module exposes.
- **Which signals carry an SLO** (chapter 02) — the subset of the axis set that gets a target, a window, a burn-rate alert, and an error budget.
- **How to assemble the stack** (chapter 03) — Prometheus Operator wiring, OTel span layout, log sampling.
- **How to price the signal** (chapter 04) — the amortised GPU-hour, the credits for cache and speculation.
- **How to defend the point** (chapter 05) — the Pareto curve and the batch / `k` / `max-num-seqs` sweep.
- **How to translate to business** (chapter 06) — the KPI delta and the cost-per-revenue-token argument.

If you find yourself debugging *why* a metric is wrong (an engine bug, a scheduler regression, a KV leak, an NCCL stall), route back to the originating module. This module operates the signal; it does not fix the engine.

3. [**The Prometheus / Grafana / OpenTelemetry Stack for Inference**](03-prom-grafana-otel-stack.md) — DCGM-exporter wired through the Prometheus Operator (`PodMonitor` / `ServiceMonitor` / `PrometheusRule`), engine-exposed metrics (`/metrics` for vLLM / SGLang / TRT-LLM) with correct relabel discipline, OTel span layout for a prefill-then-decode request (admit → queue → prefill → first-token → decode → stream-close), the trace-sampling policy (tail-based for errors, head-based for everything else), the log-sampling policy at high QPS, and the four dashboards every inference team should have.
4. [**Cost per 1M Tokens — Amortised GPU-Hour, Prefix-Cache Credit, Speculative Credit, Cost SLO**](04-cost-per-million-tokens.md) — the GPU-hour cost model (on-demand, reserved, spot, cross-cloud), the amortised fleet cost (controlplane + logging + egress + idle), the utilisation adjustment (fleet rarely runs at 100 %), the input-token cost vs. output-token cost split (prefill is compute-bound and cheap per token; decode is memory-bandwidth-bound and expensive per token), the prefix-cache credit (served-from-cache tokens cost roughly the HBM footprint not the prefill), the speculative-decoding credit (acceptance rate changes effective TPOT and so cost per output token), and the cost-per-request SLO that drops out of the per-token model.
5. [**The Throughput-vs-Latency Pareto Curve — Sweeping, Reading, Defending**](05-throughput-vs-latency-pareto.md) — the batch-size sweep (`max-num-seqs`, `max-num-batched-tokens`, `k` for speculative) that produces the curve; the TTFT-vs-TPOT shape (increasing batch raises throughput and TPOT roughly linearly, raises TTFT via queueing); the goodput envelope (throughput at or below the SLO, not throughput absolute); the three common Pareto shapes (knee, ceiling, cliff) and what each one means operationally; the one-page memo that defends your current operating point against *"can we just double throughput."*
6. [**Business Metric Tie-In — KPI per TTFT ms, Cost per Revenue Token, Is It Worth the Ask**](06-business-metric-tie-in.md) — the funnel linkage (TTFT 300 ms → 200 ms is worth `$X` per month if the product sees a measurable retention or conversion lift); the cost-per-revenue-token ratio (how much of a request's revenue goes to inference compute); the latency-attributable churn pattern (survival-curve shift after a latency regression); the memo template that lets a product manager, an engineering director, and a finance partner all read the same page and decide; the specific antipatterns ("optimise P99 to zero," "ship cheapest provider," "chase model-benchmark score") that this translation discipline exists to resist.
7. [**Boundary to `ai-infra-sre` — SRE Methodology at L30, Inference Specialisation at L35**](07-boundary-to-ai-infra-sre.md) — the mapping table from the general SRE scope of `ai-infra-sre` (level 30) to the inference-specific extensions this module adds; the hand-off list for ambiguous cases (incident command, postmortem, multi-service SLO, cross-cutting burn-rate reviews); the three common cross-boundary mistakes.

## Exercises

Each exercise carries a chapter into a reusable artefact — a decomposed-latency dashboard, an SLO document, an OTel-instrumented stack, a cost dashboard, a Pareto sweep report, a business-metric memo.

1. [**TTFT / TPOT / ITL Decomposition and Trace Wiring**](exercises/exercise-01-ttft-tpot-itl-decomposition-and-trace-wiring.md) — expose or synthesise the four latency axes on a representative engine, wire OpenTelemetry spans for the admission → prefill → decode critical path, build the per-axis Grafana panel set, and publish the decomposition for your fleet.
2. [**SLO Authoring per Workload Class**](exercises/exercise-02-slo-authoring-per-workload-class.md) — pick three workload classes on your fleet, propose a TTFT / TPOT / availability / cost SLO for each with justification, author the burn-rate alert set, and submit a one-page SLO document in the shape your SRE / product partner will sign off on.
3. [**Prometheus / Grafana / OTel Inference Stack — Base**](exercises/exercise-03-prom-grafana-otel-inference-stack-base.md) — stand up (or extend) a Prometheus Operator install that scrapes DCGM-exporter and your engine's `/metrics` with correct relabel discipline, wire an OpenTelemetry collector in front, author four dashboards (fleet, per-workload-class, per-replica, cost), and ship the stack as reproducible manifests.
4. [**Cost per 1M Tokens — Model and Dashboard**](exercises/exercise-04-cost-per-million-token-model-and-dashboard.md) — build the cost model (amortised GPU-hour, utilisation-adjusted, prefix-cache credit, speculative credit), author the per-workload-class cost dashboard, and publish a cost-attribution report for a representative one-week window.
5. [**Throughput-vs-Latency Pareto Sweep**](exercises/exercise-05-throughput-vs-latency-pareto-sweep.md) — sweep `max-num-seqs`, `max-num-batched-tokens`, and (if applicable) speculative `k` on a chosen model + hardware, plot the Pareto curve, identify the operating point against your chapter-02 SLOs, and defend it in writing.
6. [**Business-Metric Tie-In Report**](exercises/exercise-06-business-metric-tie-in-report.md) — pick a candidate optimisation (TTFT reduction, cost reduction, cache improvement, speculative adoption, hardware migration), estimate the business impact in a reasoned one-pager (what KPI, what delta, what dollar value, what risk), and present a go / no-go recommendation.
