# Chapter 06 — In-Flight Model Swap on the Serving Fleet

> A model swap is a 50 GiB file move with a 10 ms latency budget. Both sides of that sentence drive the design.

## Motivation

A quantised artefact is live only when it is serving traffic. Getting from "the artefact passed the gate" to "the fleet is serving the new variant and the old one has been retired" is the model-swap problem. On a stateless API service you flip a load-balancer rule and move on. On an LLM serving fleet you have 50 GiB of weights in HBM that cannot teleport, in-flight long-running decode streams that must not be interrupted, warm prefix caches you'd rather not throw away, and a client SLO that doesn't care about your deployment plumbing.

This chapter is the swap discipline. By the end you can:

- Draw the four swap strategies (dual-load, drain-and-replace, blue-green, in-flight weight reload) and know when each applies.
- Author the capacity constraints — does the fleet have the HBM headroom to dual-load the two variants simultaneously?
- Author the drain protocol — how to stop admitting new requests while letting in-flight ones finish without dropping a single response.
- Design the atomic routing cutover and the model-version header for client observability.
- Run the swap as a dry run and read the dashboards afterwards.

The swap discipline here is **quantisation-specific** — it addresses the HBM / dtype / kernel-recompile reality of swapping an LLM model. The broader rollout discipline (canary, shadow, response-diff, auto-rollback) belongs to module 113; this chapter owns the swap *primitive* module 113's rollouts use.

## The structural picture — what a swap must guarantee

A healthy swap satisfies five invariants:

1. **No dropped requests.** Every request accepted during the swap window returns a complete response.
2. **No wrong-model responses.** No request receives a response that was partly generated by the old model and partly by the new.
3. **Bounded latency impact.** TTFT and TPOT during the swap stay within SLO; or if they cannot, the swap is scheduled during a low-traffic window.
4. **Reversibility within a bounded window.** If the new variant proves bad, the swap can be reversed within O(seconds-to-minutes), not O(hours).
5. **Observable to the client.** The response carries the model version it was served by, so client-side regression analysis can bin outputs by variant.

Each strategy below satisfies these invariants with different capacity and complexity trade-offs.

## Strategy 1 — Dual-load (hot standby)

Both variants are loaded on the fleet simultaneously; routing shifts traffic from old to new; the old variant is drained and unloaded once the new one is proven.

### Mechanics

- The fleet is sized to hold both variants in HBM at the same time.
- The router has two upstream pools (`pool_old`, `pool_new`), each pointing at workers serving the respective variant.
- Routing ratio ramps from (100% old, 0% new) → (0% old, 100% new) over a chosen window (minutes to hours).
- At 0% old, drain `pool_old` by waiting for in-flight requests to finish, then unload the old weights.

### Capacity constraint

The dual-load window requires `HBM ≥ weights_old + weights_new + activations + reserves + KV_pool`. For a 70B BF16 base and a 70B FP8 variant, dual-loaded on the same workers:

```
HBM budget = 140 GiB (BF16 weights) + 70 GiB (FP8 weights) + reserves + KV
```

Which doesn't fit on 1× H100 80 GiB. Dual-load on the same workers requires either:

- A smaller model that fits twice.
- A multi-GPU shard (TP=4 means each GPU holds a quarter of each variant).
- A dedicated set of workers for each variant (next strategy — blue-green at the fleet level).

**When dual-load on the same workers fits:** small models, high-TP configurations, and quantised-only variants (two FP8 variants of a 70B that together are 140 GiB; still tight on 1× 80 GiB).

### Benefits

- Fastest cutover (routing-ratio change is O(seconds)).
- Instant rollback (ramp back to 100% old).
- KV cache for the old variant stays warm until the ramp completes.

### Costs

- The HBM headroom cost is the big one. Often prohibitive.
- Workers must support loading two models; most engines do not (they are one-model-per-process); so dual-load is usually done at the *fleet* level — different pods / processes serving different variants — not inside a single process.

### Variant: dual-load with a weight-level sidecar

Some engines expose an API to load a second set of weights into pre-allocated HBM in the same process. Rare; verify.

## Strategy 2 — Drain-and-replace (per-worker)

One worker at a time is drained, its weights replaced, and it is brought back into rotation.

### Mechanics

Per worker:

1. **De-register** the worker from the router (stop admitting new requests).
2. **Drain**: wait for in-flight requests to complete (or hit their max-token budget / timeout).
3. **Unload** the old weights (free HBM).
4. **Load** the new weights (populate HBM).
5. **Warm up** (CUDA graph capture, kernel JIT, prefix-cache rehydration if any).
6. **Health-check** the worker on a canary request.
7. **Re-register** the worker with the router.

Repeat until all workers are on the new variant.

### Capacity constraint

HBM-wise, only one worker's HBM is in the "loading" state at a time; no dual-load tax. The fleet's HBM headroom only has to accommodate one variant at a time.

**Throughput impact:** losing one worker shrinks capacity by `1 / fleet_size`. On a 20-worker fleet with workers that normally run at 80% utilisation, draining one worker pushes the others to ~84%. On a 4-worker fleet, draining one pushes the others to 107% — overload. Plan accordingly.

### Drain duration

Dominated by the longest in-flight request. For a chat workload with 2 048-token max output and 50 tokens/sec per request, a decode-only request can take 40 seconds. Set a drain timeout; after it, forcibly terminate the remaining in-flight requests (or let their max-token budget expire). The chapter-05 contract's `graceful_termination_seconds` field is where the timeout lives.

### Load duration

Dominated by weight-tensor copy from host (DRAM or SSD) to HBM. For a 70B BF16 model (140 GiB) over PCIe Gen4 (~25 GiB/s per direction):

```
load_time = 140 GiB / 25 GiB/s = ~5.6 seconds
```

Plus CUDA graph capture (seconds to tens of seconds) and prefix-cache warmup (variable).

### Benefits

- No dual-load HBM tax.
- Simple to reason about (one worker at a time).
- Works with any engine (no in-process reload required).

### Costs

- Fleet-wide throughput dip during each worker's drain + load.
- Serial rollout: `fleet_size × per_worker_time` end-to-end. 20 workers × 1 minute each = 20 minutes.
- Rollback requires re-draining and re-loading the old variant — not instant.

### Parallelising drain-and-replace

With sufficient fleet headroom (say, 25% spare capacity), you can drain and replace multiple workers at once. Common pattern:

```
drain-and-replace batches of ⌈fleet_size / 10⌉, waiting for health-check pass between batches
```

Reduces end-to-end time but widens the throughput dip.

## Strategy 3 — Blue-green (fleet-level)

Two full fleets exist: fleet B (blue, old variant) and fleet G (green, new variant). The router cuts traffic from blue to green atomically.

### Mechanics

1. **Pre-provision** fleet G at full capacity, loaded with the new variant, idle.
2. **Pre-warm** fleet G (prefix cache, CUDA graphs) with synthetic or shadow traffic.
3. **Cutover** at the router: switch 100% of new requests to fleet G.
4. **Drain** fleet B: in-flight requests complete; no new requests arrive.
5. **Decommission** fleet B after the drain window.

### Capacity constraint

Requires full fleet replication for the cutover window — 2× infrastructure cost during the window. For a GPU fleet this is substantial. Mitigation: the second fleet can be smaller if you time the swap during a low-traffic window.

### Benefits

- Atomic cutover (sub-second).
- Instant rollback (route back to fleet B).
- No per-worker warmup during the swap (fleet G is already warm).
- Isolation: a bad new variant can't degrade fleet B.

### Costs

- 2× infrastructure cost during the swap window.
- Prefix cache on fleet G starts cold (unless pre-warmed with shadow traffic).
- Operational complexity: two fleets, two sets of dashboards, routing configuration.

### When blue-green shines

- When the stakes of a bad swap are high (customer-facing primary model).
- When the swap window is short enough that paying 2× for an hour is cheap.
- When shadow traffic is already in use (module 113's shadow pattern composes with blue-green).

## Strategy 4 — In-flight weight reload

Reload the weights in-place in the same engine process without draining running requests.

### Mechanics

- The engine exposes an API (`reload_weights(path)` or equivalent).
- The call:
  1. **Pauses** the scheduler loop briefly.
  2. **Copies** new weights into existing HBM allocations (requires the weight shapes to match).
  3. **Updates** the engine's internal weight pointer / kernel configuration.
  4. **Resumes** the scheduler loop.
- In-flight requests' KV cache is preserved (critically — this is the point of in-flight reload). The next decode step for every in-flight request uses the new weights.

### What this is for

LoRA adapter swap. Multi-adapter serving. Hot-reload for A/B testing. **Module 106** covers the adapter case in depth; the mechanic is the same.

For a full base-model swap (BF16 → FP8), in-flight weight reload is **unusual** because:

- The weight shapes differ (FP8 is half the size of BF16, so the HBM allocation footprint changes).
- The kernels differ (the FP8 GEMM kernel is a different kernel from the BF16 GEMM).
- The engine would have to re-plan its memory layout, which is close to re-initialising the engine.

**In-flight weight reload for a dtype change is engine-specific and experimental.** Verify support before relying on it; most teams use drain-and-replace or blue-green for a dtype change.

### Where it does apply to this module

- **Precision-preserving quantisation re-tune.** You produced a new FP8 variant with recalibrated scales but the same storage shape. In-flight reload might work.
- **Weight-value correction without architecture change.** A patched FP8 variant to fix a specific layer's calibration. Likely safe to in-flight-reload.
- **Any adapter / LoRA swap** on top of a stable base. (Module 106's territory.)

### Costs

- Scheduler pause duration = few hundred milliseconds, during which admission is halted and TTFT spikes.
- Fragility: hard to roll back if the new weights are bad — the old weights are gone.
- Engine support varies.

## The drain protocol in detail

Draining is subtle; the common bugs are:

- **Admitting one more request after the de-registration signal because of in-flight queue entries.** The de-registration must be *atomic* with "stop pulling from the admission queue." Verify your engine's semantics.
- **Streaming responses mid-flight when the engine shuts down.** The HTTP connection should close cleanly (final chunk, flush, close); not abort. The engine should let the request finish or respond with a well-formed "cancelled" terminator.
- **KV cache allocated but no sequence running.** The chapter-01 of module 104's block-release discipline is the audit — on drain, pool_usage should fall to zero (or to baseline-reserved) within seconds of the last request finishing.
- **Draining faster than the longest in-flight request.** Decode of a 2 048-token response at 50 tok/s is 40 seconds. If the drain timeout is 30 seconds, that request is cut off. Set the drain timeout to match the workload's p99 completion time, not the median.

### Suggested drain protocol

```
# Pseudo-protocol
1. Health endpoint reports "draining=true"
2. Router stops routing new requests to this worker (watch the health signal, O(seconds))
3. Worker waits for admission queue to drain (empty)
4. Worker waits for running batch to finish all sequences:
      while running_sequences > 0 and elapsed < max_drain_seconds:
          sleep 100ms
5. If any sequences remain at timeout:
      send a cancellation terminator to clients
      (optional: continue decoding to force a clean HTTP close)
6. Health endpoint reports "ready_for_shutdown=true"
7. Orchestrator shuts down the worker process
8. (For drain-and-replace) relaunch with new weights
```

Each step has a timeout and a dashboard counter. On drill, the counters are what you watch.

## The atomic routing cutover

At the router, the cutover must be atomic in the eyes of a request:

- A request that resolves the service name before the cutover must land on the old variant and get a full response.
- A request that resolves after the cutover lands on the new variant.
- No request sees "both" or "neither."

### Mechanisms

- **DNS-based routing** — atomic at the resolution step but weak globally (DNS TTLs cause lag). Not recommended for fast swaps.
- **Layer-7 router with explicit routing rules** (Envoy / NGINX / HAProxy / vendor-ingress) — atomic at the connection level. Set the rule, in-flight connections drain under the old rule, new connections use the new rule. **The recommended mechanism.**
- **Service-mesh traffic shifting** (Istio / Linkerd `VirtualService` weight) — fine-grained, atomic at the request level. Good for ramp-based cutover.
- **Load-balancer target-group swap** (AWS ALB / GCP LB) — atomic at the ALB config level; new connections hit the new target group.

**Operator rule:** the cutover mechanism must support atomic weight change at the per-request granularity. Avoid any mechanism that cuts over at the DNS or TCP-connection level and leaves a window where a request can hit "either" fleet.

## The model-version header

Every response from a serving worker should carry a header that identifies the variant that produced it:

```
HTTP/1.1 200 OK
...
X-Model-Variant: org/llama-3-70b-instruct/fp8-e4m3-static/v2
X-Model-Artefact-Id: sha256:...
X-Served-By: worker-fleet-g-pod-04
```

(Header names are a choice; the field names are the point.)

### Why this matters

- **Client-side analysis.** Downstream regression analysis bins outputs by variant. Without the header, "did the swap regress quality" is unanswerable.
- **Incident response.** A customer-reported quality issue timestamped during the swap window can be attributed to the specific variant that served it.
- **Audit.** For compliance / safety reviews, response-level provenance is often required.

The header must be set *at the worker*, not the router, so it reflects what actually served the request (routers can be wrong; workers know).

## Reversibility and rollback

The art of rollback is the art of making the pre-swap state recoverable within an SLO.

### Per-strategy rollback latency

| Strategy | Forward swap time | Rollback time | Rollback mechanism |
|---|---|---|---|
| Dual-load | Minutes (ramp) | Seconds | Reverse the routing ratio |
| Drain-and-replace | Minutes to tens of minutes | Minutes to tens of minutes | Repeat drain-and-replace with old variant |
| Blue-green | Seconds (cutover) | Seconds | Reverse the routing cutover |
| In-flight reload | Hundreds of ms | Hundreds of ms (if supported) or needs restart | Reload old weights (if a copy is still on disk) |

**Rollback preconditions:**

- The old variant artefact must still be in the registry and still passable through load-time signature verification.
- The old variant must still be a legal deployment target (not deprecated, not licence-restricted).
- The hardware and kernel compatibility that the old variant required must still exist on the fleet.

**Rollback escalations:**

- A rollback that doesn't complete in O(bounded) time is an incident. Alert.
- A rollback that fails to restore the pre-swap behaviour (because of KV cache cold-start, warmup, or workload shift) is a secondary incident. Diagnose separately.

## Observing the swap

The dashboards you watch during a swap:

- **Routing ratio** — the planned ramp vs. the observed ratio. A gap means routing is misconfigured or something is ignoring the signal.
- **Per-variant TTFT, TPOT, E2E** — the new variant's SLO numbers must stay within bounds. Divergence > a threshold triggers rollback.
- **Error rate per variant** — any 5xx on the new variant above baseline is a signal.
- **KV cache occupancy** — on drain, pool_usage falls; on load, it ramps up as traffic arrives.
- **GPU memory per worker** — load events are visible as a step function.
- **Scheduler iteration time** — a sudden increase on the new variant is a slow kernel / wrong-dtype signal.
- **Model-version-header distribution** — fraction of responses tagged with the new variant should match the routing ratio within sampling noise.

Alert on any of these diverging during the swap window; auto-rollback where possible (module 113's territory).

## Running the swap as a dry run first

Before the first production swap of a new quantised variant, do a **dry run** against a staging environment that mirrors production in all operational dimensions:

- Same engine version, driver version, GPU model.
- Same scheduler config.
- Same router mechanism.
- Representative traffic shape (shadow-replayed or synthetic).

The dry run surfaces:

- Load time surprises (bigger / smaller than the arithmetic suggested).
- Scheduler-pause surprises on in-flight reload.
- KV cache warmup time.
- The actual drain timeout the workload needs.
- Observability gaps (which dashboards don't update as expected).

Dry run output is the runbook (next section).

## The swap runbook

A per-model-per-strategy runbook that lives alongside the artefact (chapter 05's contract has a field for it):

```
# Swap Runbook: Llama-3-70B FP8 E4M3 v2 → v3
Strategy: drain-and-replace, batches of 2
Pre-flight checklist:
  [ ] v3 artefact promoted to prod registry
  [ ] v3 signature verified
  [ ] v3 chapter-04 gate passed
  [ ] Staging dry-run completed within last 72 hours
  [ ] On-call engineer identified
  [ ] Rollback artefact (v2) still in registry
Timing:
  Planned window: Thursday 02:00 UTC (lowest traffic)
  Expected duration: 25 minutes
Steps:
  1. [T-10min] Announce in #inference-alerts
  2. [T=0]    Begin batch 1 (workers 1-2): drain, replace, health-check
  3. [T+5m]   Begin batch 2 (workers 3-4): ...
  ...
Monitoring during swap:
  - Dashboard: ...
  - Alert threshold: TTFT P99 > 1.5× baseline → auto-pause
  - Model-version-header ratio: expected 50/50 at T+15 minutes
Rollback trigger:
  - Error rate > 2× baseline on v3 for 2 consecutive minutes
  - TTFT P99 > 2× baseline on v3 for 2 consecutive minutes
  - Any 5xx from loading
Rollback procedure:
  - Halt batch rollout
  - Re-queue completed batches for v2 drain-and-replace
  - Expected rollback duration: 10 minutes
Post-swap:
  [ ] All workers reporting v3 in model-version-header
  [ ] Perplexity canary re-run on v3 serving (should match artefact's gate result)
  [ ] Fleet-wide dashboards nominal for 60 minutes
  [ ] Post-swap note in #inference-changelog
```

The runbook is the operational artefact; the dry run is where it is first exercised.

## Common misreadings

- **"The swap is just a Kubernetes rolling update."** Rolling update draining doesn't understand LLM in-flight requests (which can be minutes long for long-form responses). You need an LLM-aware drain protocol.
- **"Blue-green is always better."** It is 2× infrastructure cost during the window. For non-critical workloads or capacity-constrained fleets, drain-and-replace is often correct.
- **"In-flight weight reload is universal."** It is engine-specific, experimental, and typically only clean for same-shape reloads (adapter swap, scale recalibration). A dtype change often cannot be in-flight-reloaded.
- **"The model-version header is cosmetic."** Without it, post-swap regression analysis is manual guesswork. The header is non-negotiable.
- **"Rollback is a secondary concern."** Rollback is the primary concern — the swap plan is incomplete until it includes a tested rollback within the SLO.
- **"Dry runs are overkill."** The first production swap of a new quantisation flavour will surface at least one surprise. Dry run cheaply; discover it in staging.
- **"The scheduler pause on in-flight reload doesn't matter."** It matters if clients observe TTFT spikes above SLO. Measure.

## Summary

- Four swap strategies: **dual-load** (hot standby, fast cutover, high HBM cost), **drain-and-replace** (per-worker, no dual-load tax, serial duration), **blue-green** (atomic cutover, 2× infrastructure cost), **in-flight weight reload** (fastest, engine-specific, usually for same-shape reloads not dtype changes).
- The five invariants a swap must preserve: **no dropped requests**, **no mixed-model responses**, **bounded latency impact**, **reversibility within SLO**, **client observability via model-version header**.
- The **drain protocol** has well-defined phases: de-register, admission-queue-drain, running-batch-drain-with-timeout, cancellation if timeout exceeded, ready-for-shutdown signal. Each phase has a dashboard counter.
- The **cutover** must be **atomic at the per-request granularity** — layer-7 router or service mesh, not DNS or TCP-connection switching.
- The **model-version header** on every response binds the output to the artefact that produced it; non-negotiable.
- Every swap has a **rollback procedure** with a bounded latency. The rollback artefact must still be in the registry and compatible.
- A **dry run** against staging precedes the first production swap of any new variant; the dry run output becomes the **runbook** attached to the artefact.
- This chapter owns the swap **primitive**; the full rollout discipline (canary, shadow, response-diff, auto-rollback at fleet scale) belongs to module 113, which consumes this chapter's primitives.
