# Module 111 — Inference API Design and Protocols

> **Role:** AI Inference Engineer · **Level:** L35 (AI Infrastructure family) · **Hours:** 14

Modules 102–110 made the engine fast, the fleet elastic, the signal observable, and the dollars accounted for. None of that is reachable from a client until there is an API in front of it. This module is the serving front door: the request-and-response protocol, the streaming contract, the structured-output and tool-calling plumbing, the server-side Model Context Protocol surface, and the request-shape discipline that makes retry, rate-limit, authentication, and tenant-isolation correct at the ingress. The "OpenAI-compatible" phrase has become an industry default because every engine wants client portability, but *compatible* is a word with a lot of drift inside it; this module teaches the drift honestly.

By the end of it you can:

- **Implement an OpenAI-compatible API surface** at the serving front door — `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, the newer `/v1/responses` shape, and the multimodal / audio endpoints where the engine supports them — and reason about the compliance-drift tax of *OpenAI-compatible* between engines (parameter aliases, enum drift, streamed-chunk shape, finish-reason semantics, tool-call object shape).
- **Implement streaming at production quality** — Server-Sent Events (SSE) as the primary transport per the WHATWG HTML Living Standard, WebSocket as the bidirectional alternative for audio / full-duplex workloads, chunk-boundary discipline, back-pressure on the engine → client path, client-disconnect handling with graceful request cancellation, and the token-flush cadence that keeps TTFT honest without destroying per-request CPU.
- **Implement structured output and constrained decoding at production quality** — JSON Schema enforcement at the sampler, Pydantic models as schema source, Outlines and XGrammar as constrained-decoding backends, the grammar-vs-regex-vs-schema trade-off, and the correctness-vs-latency cost of each enforcement mode.
- **Implement tool-calling at production quality** — the tool-choice protocol (`auto`, `none`, `required`, a named tool), parallel tool calls, the tool-response round-trip, streaming behaviour during the tool-call phase, and the provider-specific extensions (Anthropic's `tool_use` blocks, OpenAI's `tool_calls` array) that your compatibility layer must translate.
- **Reason about Model Context Protocol (MCP) on the server side** — exposing an inference endpoint behind an MCP server per the [MCP specification](https://modelcontextprotocol.io/specification), the auth model (OAuth 2.1 plus the Resource Server pattern), the three capability kinds (Resources, Tools, Prompts), and the implications for the inference platform when the client is an MCP-aware agent rather than a chat SDK.
- **Author request-shape discipline** — retry semantics (safe retry, unsafe retry, `Idempotency-Key` headers per Stripe's and the IETF draft's pattern), back-pressure headers (`Retry-After`), rate-limit headers (`RateLimit`, `RateLimit-Policy` per IETF draft and the legacy `X-RateLimit-*` set), request-ID propagation (W3C `traceparent` and vendor `x-request-id`), the authentication model (API key, OAuth 2.1 bearer tokens, short-lived STS tokens), and tenant isolation at the ingress.
- **Cite the boundary to [`llm-application-developer`](https://github.com/ai-engineering-curriculum/llm-application-developer-learning) and [`rag-engineer`](https://github.com/ai-engineering-curriculum/rag-engineer-learning) (L25 peers, AI Engineering family)** — those tracks *consume* this API from the application side (prompt engineering, agent design, RAG pipeline construction); this module owns the *server-side implementation* of the contract they consume.

The level-20 track covers plain HTTP, OAuth, TLS, and the generic REST discipline that this module assumes.

## The core framing

The serving front door looks like a REST API and *is not quite one*. Four asymmetries drive every design decision in this module:

- **A response is a stream, not a payload.** The client POSTs once and consumes tokens over seconds. SSE is the primary transport for text streaming. The HTTP semantics (status code, headers, body shape) must be correct *before the stream starts*, because once the first `data:` frame flushes you cannot change your mind. Chapter 02 names the discipline.
- **"OpenAI-compatible" is a moving target.** OpenAI's own API evolves (chat completions → responses, strict JSON mode → structured outputs, function calls → tools → parallel tools). Every engine implements some subset of some version. A client that works against vLLM 0.6 may fail against SGLang 0.4 against TRT-LLM 0.14 against OpenAI itself — same request, four finish-reason strings. Chapter 01 names the drift and the compatibility gate.
- **Structured output and tool calls are sampler-level, not response-level.** Enforcing a JSON schema post-hoc (validate the final string, retry on failure) is strictly worse than enforcing it at the sampler (reject any token that would make the output invalid). Outlines, XGrammar, and native engine support implement the latter; chapter 03 teaches the trade-offs and chapter 04 reuses them for tool-call arguments.
- **The ingress is where tenant-isolation and rate-limit discipline live.** The engine is a shared resource; the ingress must enforce quotas, propagate trace context, assign request IDs, and translate authentication tokens to internal identity *before* the request consumes a KV slot. Chapter 06 writes the pattern; chapters 03 and 04 assume the ingress is already enforcing it.

Those four asymmetries also set the chapter order: the OpenAI-compatible surface first (01), the streaming transport that carries it (02), the structured-output discipline for the response body (03), the tool-call protocol as a specialisation of structured output (04), the MCP server-side exposure for agent-shaped clients (05), the request-shape discipline that makes the ingress correct (06), and the boundary to the L25 consumer peers that keeps this module's scope honest (07).

## Boundary against `llm-application-developer` and `rag-engineer` (L25)

The AI Engineering family at L25 owns the *application* side of the inference contract. If your diagnosis lands on *"the prompt doesn't produce the right JSON,"* *"the agent loop retries a tool call incorrectly,"* *"the RAG chunker uses too many tokens,"* *"the system prompt's instruction hierarchy is wrong,"* or *"the user-facing streaming UI flickers" — that is the L25 consumer track's scope. Go there first.

The **server-side protocol implementation** is this module:

- The HTTP surface layout (route map, request / response schema, error catalogue, header set).
- The SSE and WebSocket transport implementation (framing, back-pressure, cancellation).
- The constrained-decoding backend integration (Outlines / XGrammar / native) and the schema-to-sampler wiring.
- The tool-call parser and emitter on the engine side (not the agent loop on the client side).
- The MCP *server* implementation (not the MCP client loop inside an agent).
- The ingress policy (auth, rate-limit, idempotency, tenant-isolation, request-ID propagation).

Rule of thumb: *if the question is "how does the application use this endpoint," that is the L25 peer. If the question is "how does the endpoint behave when it is used," that is this module.*

Chapter 07 formalises the boundary with a mapping table, a hand-off list, and the three common cross-boundary mistakes.

## Boundary against the performance peer (`ai-infra-performance`, L35)

The performance peer owns the kernels that produce the tokens. This module owns the HTTP framing that carries them. If TPOT regresses because a GEMM dispatches to a slower kernel — performance peer. If TTFT regresses because the SSE flush interval buffers the first token for 300 ms — this module. The split stays clean.

## Exercises

Each exercise carries a chapter into a reusable artefact — a compatibility harness, a streaming ingress, a constrained-decoding gateway, a tool-call translator, an MCP endpoint, a request-shape policy document.

1. [**OpenAI-Compatible API Walkthrough Across Engines**](exercises/exercise-01-openai-compatible-api-walkthrough-across-engines.md) — exercise the same request against two or more engines (vLLM / SGLang / TRT-LLM / an external hosted API), catalogue the drift observed in response shape / finish reason / streamed-chunk layout / error object, and publish a compatibility report.
2. [**Streaming SSE Production Patterns**](exercises/exercise-02-streaming-sse-production-patterns.md) — implement an SSE streaming proxy in front of an engine with chunk-boundary discipline, back-pressure, client-disconnect cancellation, and heartbeat; prove correct behaviour against a scripted set of adversarial client patterns (slow reader, early close, mid-stream abort).
3. [**Structured Output Schema Enforcement Drill**](exercises/exercise-03-structured-output-schema-enforcement-drill.md) — pick a non-trivial JSON Schema (nested, with enums and conditional required-fields), run it in post-hoc / JSON-mode / strict-schema / grammar modes against the same engine, measure the latency tax per mode, and publish the per-mode correctness and latency table.
4. [**Tool Calling Protocol Plumbing**](exercises/exercise-04-tool-calling-protocol-plumbing.md) — implement a tool-call translator that accepts an OpenAI-shape request and routes it to either an Anthropic-shape or OpenAI-shape backend, handles parallel calls, streams through the tool-use phase, and completes the round-trip without losing a chunk.
5. [**MCP Server-Side Exposure Walkthrough**](exercises/exercise-05-mcp-server-side-exposure-walkthrough.md) — stand up an MCP server that exposes an inference endpoint as a Tool, implement capability discovery, wire the OAuth 2.1 Resource Server pattern, and prove an MCP-aware client can discover, authorise, and invoke the capability.
6. [**Request-Shape Discipline and Ingress Authoring**](exercises/exercise-06-request-shape-discipline-and-ingress-authoring.md) — author the ingress policy (idempotency key handling, retry semantics for streams, rate-limit headers, `traceparent` propagation, auth translation, per-tenant quota enforcement) and prove correctness against a fault-injection test suite.
